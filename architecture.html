Architecture · 平台架构

六层 + 一个底座

层是功能边界，底座是数据边界。层可以按阶段上线，底座必须一次定对——项目主键、碳量守恒、事件时间线这三件事改起来最贵。

六层模块清单 数据底座与实体 守恒约束 技术栈选型
01 FUNCTIONAL LAYERS

每层交付什么、谁在用、留下什么数据

功能设计的验收标准不是「页面做出来了」，而是这一层往数据底座写了什么。写不出数据的模块就是装饰。

L1

孵化层 JebiStarter

让早期项目在进入任何融资之前，先完成「可融资化」与「可测量化」。

  • 项目注册与诊断 — 产业链环节（种植/加工/烘焙/包装/物流/门店）、所在地、碳项目类型、融资阶段
  • 孵化工作流 — 里程碑清单：商业计划、碳基线、供应链数据、MVP，平台跟踪完成度
  • 碳基线预评估 — 内置排放因子库 + IPCC 方法学，产出初步碳足迹与减排潜力评分（不可交易）
  • 社区预热 — 预上线项目页，收集关注、预约投资、粉丝反馈，为众筹蓄水
写入 CarbonProfile门户：项目方 / 社区
L2

社区股权众筹层 Wefunder

合规地把粉丝与社区资金导入项目，并把碳权益的穿透安排写进 SPV 结构。

  • 发行页面 — 故事、融资目标、股权/SPV 结构、资金用途、碳权益说明、风险披露（强制区块）
  • 认购与托管 — 承诺认购 → 托管账户 → 达标交割；状态机：草稿 / 待签 / 已承诺 / 已托管 / 已交割 / 已取消
  • SPV 管理 — 多投资者集中持股，记录 SPV 层权益分配与碳权益穿透比例
  • 投资者组合页 — 按已确认/待处理/已取消分组，合同 PDF 下载、投资详情
写入 Investment / SPV门户：社区投资者
L3

机构资本与基金层 Jebi Capital

承接成长期项目与机构资金，管理基金与 SPV 的全生命周期。

  • 机构数据室 — 尽调材料、核证报告、财务模型、供应链合同，权限分级到文件夹级
  • 基金管理系统 — 基金设立、LP 认购、capital call、费用计算、NAV 估算、carry 瀑布
  • SPV 管理 — 设立、银行/托管对接、分配记录、税务文件
  • 并购与退出 — 退出事件登记、收益分配、股权与碳权益对价拆分
写入 Fund / CapitalCall门户：机构 / 基金管理
L4

碳权益层 贯穿层 · 核心

同时服务「投资企业获得碳权益」与「基金获得碳收益」两个目标，但绝不把股权投资等同于碳购买。

  • 碳资产档案与台账 — 方法学、基线、监测期、预计量、核证状态、登记簿 ID；平台不做注册处，做注册处的聚合视图
  • MRV 工作流引擎 — 数据接入 → 监测报告 → 核证审核 → 签发 → 转移 → 分配或注销，状态机 + 不可篡改审计轨迹
  • 碳权益合同管理 — 条款库（优先购买权、分配比例、远期价格公式、回购替换），签发后自动计算应得吨数
  • 远期采购与注销 — 意向 → 条款清单 → 法律文件 → 注销指令 → 登记簿 API 执行 → 证书回写
  • 企业披露支持包 — 台账报表对齐范围三/抵消/移除字段，但不承诺合规结论
写入 VerificationBatch / Entitlement / Retirement
L5

退出与收益分配层

让基金与投资企业在一屏看到「股权 + 碳权益」的双重收益。

  • 双重收益仪表盘 — 股权价值变动 / 已实现碳权益收益 / 未实现碳权益存量
  • 退出事件处理 — IPO / 并购 / 老股转让，股权对价与碳权益对价分别计算、分别分配
  • carry 计算 — 是否含碳权益收益需在基金合同预先定义，系统支持两种口径配置
写入 ExitEvent / Distribution
L6

合规与风控层 横贯

把证券合规、碳市场合规、反洗钱、数据保护做成可配置工作流，而不是事后补文件。

  • 发行合规配置 — 按发行类型（众筹/私募/基金）挂不同披露模板与审批流
  • VASP 触发判断 — 代币化模块由持牌实体运营或与持牌托管方合作，平台不直接托管私钥
  • KYC / AML — 统一身份服务，按门户与交易类型配置核验等级
  • 数据保护 — 农户与供应链数据分级、脱敏、审计日志
写入 ComplianceCase / AuditLog
02 DATA FOUNDATION

数据底座：一个主键，两条分支，一个汇合点

Project 是唯一主键。左侧资本域逐层分裂（轮次 → SPV → 投资），右侧碳域逐层收敛（批次 → 权益 → 注销）。两者只在合同上耦合。

Fig.2 — 一个项目 → 多个融资轮次 → 多个 SPV → 多笔投资；一个核证批次 → 可拆成多条注销记录。CarbonContract 是唯一跨域实体。

实体清单（12 个核心对象）

  • Project — 主键，承载所有资本与碳事件的归属
  • FinancingRound / SPV / Investment — 资本域
  • Fund / Commitment / CapitalCall / Distribution — 基金域
  • CarbonProfile — 碳基线、方法学、预计减排量（1:1）
  • VerificationBatch / CarbonEntitlement / Retirement — 碳域三层
  • CarbonContract — 权益条款、远期采购、优先购买权
  • Event — 统一事件总线（append-only）

事件总线：一条时间线的实现方式

所有状态变更写成不可变事件，而不是就地改字段。业务表是事件流的物化视图。

event_id project_id type actor E-1042 P-0007 round.closed capital E-1043 P-0007 batch.verified mrv E-1044 P-0007 ent.allocated carbon E-1045 P-0007 carbon.retired enterprise E-1046 P-0007 exit.closed fund

→ 项目时间线、投资人通知、披露报表、审计追溯全部由同一事件流派生。

03 INVARIANT

碳量守恒：任何时刻不允许超额分配

这是全平台唯一一条数据库级硬约束。它不是业务规则，是防欺诈机制——双重计算（double counting）在碳市场是刑事风险，不是会计差错。

// 每个核证批次，任何时刻必须满足： issued(batch) − Σ allocated(entitlement) − Σ retired(retirement) − Σ sold(external_transfer) − reserve(batch) = 0 // 分配时的事务性校验（伪代码） BEGIN TRANSACTION; SELECT issued FROM verification_batch WHERE id = :batch FOR UPDATE; SELECT coalesce(sum(t),0) FROM entitlement WHERE batch_id = :batch; IF used + :new_t > issued THEN RAISE OVER_ALLOCATION; INSERT INTO entitlement ...; COMMIT;

强制手段：行级锁 + CHECK 约束 + 每日对账任务，三者缺一不可。

约束 1
签发即锁定量。VerificationBatch 的 issued_tons 只能由登记簿回调写入，平台内不可编辑。
约束 2
注销不可逆。Retirement 一旦提交，对应批次余额永久扣减；修正只能新增反向记录并留痕。
约束 3
用途排他。每条 Entitlement 必须且只能标记一种去向：scope3 / offset / resale / reserve。
约束 4
跨批次不可挪用。批次 A 的余额不能用于满足批次 B 的分配，即使同项目同方法学。
04 TECH STACK

技术选型：模块化单体起步

按域拆包，不按域拆服务。碳域的事务一致性要求很高，过早微服务化会带来分布式事务与对账地狱。

层次建议理由 / 约束
前端 多门户共享组件库；项目方与社区端偏「产品目录 + 仪表盘」，机构端偏「数据室 + 台账」 同一套设计 token，不同信息密度。机构端表格优先，社区端卡片优先。
后端 模块化单体：project / capital / carbon / compliance 四域分包，共用事务边界 碳量守恒需要跨表行锁；跨服务无法保证。先单库单事务，规模化后再按域切。
数据层 PostgreSQL 存台账与关系；核证文件与证书走对象存储；审计日志 append-only（只插不改） 金额与吨数统一用 numeric，禁止 float。所有金额双记录：原币 + 结算币。
链上（可选） 如需代币化，链上记录作为登记簿的补充，不替代法定登记 MVP 不上链。上线即触发 VASP 判断与托管合规成本。
集成 登记簿 API（Verra / Gold Standard / Puro.earth）、支付与托管、KYC 服务、电子签、基金会计系统 登记簿 API 全部做成适配器接口，统一内部 RegistryPort，避免绑定单一标准。
权限 RBAC + 项目级数据隔离：机构只能看到被授权项目的数据室 行级安全策略在数据库层实现，不只在前端隐藏菜单。
可观测 事件流回放、对账日报、双重计算告警、合规事件看板 告警必须落到人：每条告警绑定责任角色与 SLA。
D1

项目域

Project、CarbonProfile、里程碑、文档。写入频率低，读取频率高。

D2

资本域

Round、SPV、Investment、Fund、CapitalCall。金额一致性要求最高。

D3

碳域

Batch、Entitlement、Retirement、Contract。守恒约束与审计轨迹的核心。

D4

合规域

KYC、发行豁免、审批流、告警。横切所有域，只读为主。
