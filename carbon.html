Layer 04 · 碳权益层

让减排量变成可分配、可审计、不可重复计算的合同权利

这一层同时服务两件事：投资企业拿到可用于披露的碳权益，基金拿到碳收益。但它必须守住一条底线——碳权益是投资协议的附属合同权利，不是可自由转让的证券，也不是「买了碳」。

碳资产台账 MRV 状态机 权益合同 双重计算防火墙 注销与披露
01 CARBON LEDGER

碳资产档案：平台是注册处的「聚合视图」，不是注册处

法定所有权永远在登记簿上。平台台账记录的是谁有权向谁主张多少吨——两者分离，但必须随时能对上。

档案字段含义来源
project_id绑定唯一项目主键平台
methodology方法学与版本（如 AMS-I.F / VM0042）项目方 + 核证方
baseline基线情景与基线排放量项目方
核证后锁定
monitoring_period监测期起止、报告周期项目方
estimated_removal预计减排/移除量（tCO₂e/年）预评估模型
verification_status未核证 / 审核中 / 已签发 / 已驳回MRV 引擎
registry / registry_id登记簿名称与登记号Registry API
vintage减排量产生年份核证批次
buffer_pct缓冲池扣减比例（移除类项目）标准规则
sdg_tags附带可持续发展目标标签项目方

CarbonProfile 与 Project 为 1:1。档案一旦进入核证，基线字段只读。

登记簿层（法定）

Verra / Gold Standard / Puro.earth 持有项目登记、签发、转移、注销的最终事实。平台通过 API 只读拉取，并订阅状态变更。

RegistryPort 适配器Webhook + 定时对账

平台台账层（合同）

记录「谁有权获得多少吨、什么类型、什么 vintage、什么优先权」。这是内部权益账，可以与登记簿持有人不同名。

CarbonEntitlement用途排他标记
对账规则
每日自动比对：登记簿余额 ≥ 台账未注销余额 + 待分配余额。出现缺口立即冻结该项目的分配与注销功能，转人工核查。
为什么不做注册处
做注册处意味着承担登记、防重复、争议裁决责任，并需取得相应资质。做聚合视图，风险边界清晰得多。
02 MRV ENGINE

MRV 状态机：七步，每一步都有唯一责任人

数字 MRV 的四个核心组件——项目注册、验证、核证、影响追踪——在这里落成一条带状态、带权限、带证据链的流水线。

Fig.3 — 状态机不可跳步：没有核证报告就不能填签发量，没有 registry_id 就不能分配权益。
1

数据录入 项目方

支持两条通道：小农户用结构化表单 + 照片凭证（手机端、离线草稿）；加工厂/仓储用 API 或 IoT 直连（电表、冷库温度、水表）。每条数据带时间戳、设备号、上传人。

输入 活动数据 / 排放因子→落库 MonitoringRecord
2

监测报告生成 系统

按方法学模板自动汇总周期内数据，计算减排量，标记异常值与缺失项。报告为快照，生成后不可回改；数据更正走新版本。

输出 监测报告 v1/v2…→校验 完整性 / 异常值
3

核证方审核 第三方

核证方在独立门户接收任务，逐项比对报告、原始凭证与 IoT 时序。可提问、可驳回。所有批注留痕。看不到项目的融资金额与股权结构。

输入 监测报告 + 证据包→输出 审核意见 / 驳回清单
4

核证报告签发 核证方

填写核证量（tCO₂e）并签署。此动作即触发守恒校验：核证量进入 VerificationBatch 成为 locked 余额，平台内不可再编辑。

输出 核证报告 PDF + issued_tons→校验 守恒预检
5

登记簿签发 / 转移 Registry API

通过适配器向 Verra / GS / Puro 申请签发或转移持有账户，回写 registry_id 与持有人。平台账本与登记簿账本的唯一强制同步点。

输出 registry_id / holder→校验 余额对账
6

碳权益分配 平台 / Admin

按 CarbonContract 的比例与优先顺序自动计算各受益人应得吨数，生成 CarbonEntitlement 记录并标记用途（scope3 / offset / resale / reserve）。

输入 签发量 + 合同条款→输出 Entitlement 明细
7

注销或出售 企业 / 基金

企业下达注销指令（用途 + 受益人具名），平台校验归属与排他标记后调用登记簿 API 执行；基金则按协议对外出售或结转。两者互斥。

输出 注销证书 / 交易凭证→写入 披露台账

审计轨迹（append-only）

每次状态跃迁写一条不可变审计记录：who · when · what · before → after · evidence_hash。任何人不得删除，只能追加。

双通道数据接入

  • 手工 — 表单 + 图片/PDF 凭证，移动优先，弱网可保存草稿
  • API — 加工厂 ERP、冷库温控、电表；按设备绑定项目与监测点
  • IoT — MQTT 上行，按小时聚合，异常值不丢弃只标记
红线
核证方不能同时是项目方关联方；平台不代核证方签发。角色冲突检测写进入驻审核。
03 ENTITLEMENT CONTRACTS

合同条款库：把「应该给多少吨」写成可计算字段

碳权益不是一句承诺，是一组参数。条款必须结构化——否则每次分配都要律师手工算一遍。

条款作用触发事件系统行为
分配比例签发量在投资企业 / 基金 / 平台之间的拆分（如 60 / 35 / 5）batch.verified自动生成 Entitlement，比例之和必须 = 100%
优先购买权企业有权在对外出售前按公式价优先购入entitlement.available生成 30 天选择窗口，逾期自动释放
远期采购价公式以指数/固定价/区间形式约定未来交割价delivery.due按公式计算结算价，生成应付通知
回购 / 替换核证被撤销或项目失败时的补偿安排batch.reversed冻结待分配余额，触发替换批次或退款流程
vintage 限制限定可接受的减排量年份分配计算不符 vintage 的批次不进分配池
用途限制约定只能用于注销，不得转售retirement / resale在 Entitlement 上写入不可变用途锁
计算示例
批次签发 1,000 tCO₂e，合同比例 企业 60% / 基金 35% / 平台 5% → 企业 600 t、基金 350 t、平台留存 50 t。企业当季注销 200 t，则：已分配 600、已注销 200、剩余权益 400。报表同时呈现三个数字，不合并。
04 ANTI-DOUBLE-COUNTING

双重计算防火墙：一吨只能去一个地方

最容易出事的场景不是黑客，是好心的重复使用——项目方把同一批碳既卖给企业做抵消，又计入自己的减排宣传。系统必须在数据层拦住它。

Fig.4 — 用途标记写在 Entitlement 上，不可为空、不可多值。这是全平台最重要的一个枚举字段。
CHECK 1

写入时校验

分配、注销、转售三个接口共用同一把行级锁；事务内校验 batch 余额，失败即回滚。

CHECK 2

跨年比对

同一 vintage 的吨数在年末做「用途唯一性扫描」，发现同一吨出现在两条路径即冻结项目。

CHECK 3

对外声明一致性

项目方提交的品牌宣传减排声明需与台账对账；企业披露包内嵌「未重复主张」声明模板。

05 RETIREMENT & DISCLOSURE

注销：不可逆的六步，和一份不承诺结论的报表

1

发起注销指令

企业选择项目 / 批次 / 吨数 / vintage，填写注销目的（自愿抵消、客户产品碳中和、合规履约）与受益人是否具名。

2

归属校验

校验该 Entitlement 余额充足、未被用途锁定、未处于优先购买权窗口内。

3

双重计算校验

确认这批吨数未计入任何一方的范围三或减排声明；若已计入，阻止并提示先撤销声明。

4

登记簿执行

调用 Registry API 提交注销，注明注销目的与受益人。等待登记簿确认（异步）。

5

台账锁定 + 证书生成

确认回调后，台账余额永久扣减，生成注销证书（PDF + 唯一编号），记录写入 append-only 日志。

6

回写披露台账

注销量进入企业的年度碳权益台账，自动带入披露支持包的数据字段。

注销证书字段

  • 项目名称与登记号
  • 标准与方法学（Verra VCS / Gold Standard / Puro）
  • vintage、吨数、批次号
  • 注销目的（beneficial use）
  • 受益人名称（企业可选具名或匿名）
  • 注销时间、登记簿交易号
  • 证书唯一编号 + 验真链接/哈希

企业披露支持包（数据准备，非合规结论）

  • 投资明细 — 项目、轮次、金额、持股比例
  • 碳权益明细 — 获得吨数、已注销、未注销余额
  • 分类字段 — 减排 vs 移除、vintage、标准、方法学
  • 声明区 — 双重计算声明、未重复主张声明模板
  • 导出 — CSV / XLSX / PDF，字段命名对齐主流披露框架
免责
平台只提供数据与凭证，不对任何披露框架下的合规性或鉴证结论负责。此句必须出现在每份导出文件页脚。
